# CLAUDE.md

UI end-to-end tests for [saucedemo.com](https://www.saucedemo.com).
Stack: **Playwright + TypeScript (strict) + playwright-bdd** (Gherkin).

I'm building this project myself, step by step, one pull request per feature. Claude helps me with
it, so work on the current task only: don't create files, folders or layers for things we haven't
reached yet.

## Commands

| Command                                                | Purpose                                                          |
| ------------------------------------------------------ | ---------------------------------------------------------------- |
| `npm test`                                             | Generate specs with `bddgen`, then run all tests in all browsers |
| `npm run test:smoke` / `npm run test:regression`       | Run only scenarios with that tag                                 |
| `npm test -- --project=chromium -g "<scenario title>"` | Run one scenario (fastest loop)                                  |
| `npx bddgen`                                           | Generate specs; prints a snippet for every missing step          |
| `npm run branch -- create <type>/<name>`               | Create a branch from the latest `main` (name is validated)       |
| `npm run check`                                        | typecheck + eslint + prettier. **Run before finishing any task** |
| `npm run allure:generate` / `npm run allure:open`      | Build and open the Allure report from `allure-results/`          |
| `npm run lint:fix`                                     | Auto-fix ESLint issues                                           |
| `npm run format`                                       | Format everything with Prettier                                  |

## Structure

```
features/<domain>/*.feature  WHAT is verified, in business language (Gherkin)
features/steps/              step definitions and custom parameter types
src/pages/                   Page Objects: locators and actions, one class per page
src/pages/components/        parts shared by several pages (header, footer)
src/fixtures/index.ts        gives steps their page objects; exports Given/When/Then/expect
src/test-data/               users and other reusable data
src/utils/                   helpers, for example `authenticateAs` (login through a cookie)
src/config/env.ts            typed environment config; credentials come from `.env`
allurerc.mjs                 Allure report settings (grouping, history)
site/                        source of the GitHub Pages site; the Allure reports go to `/allure/`
scripts/assemble-site.mjs    builds the Pages site: `site/` plus the five newest dated reports
scripts/branch.mjs           the branch naming standard: `check` a name, `create` a branch
scripts/commit-message.mjs   the commit message standard, used by the commit-msg hook and CI
tests/seed.spec.ts           start state of the AI test agents (logged in standard user)
specs/                       test plans written by the planner agent
.mcp.json                    the Playwright test MCP server used by the agents
.claude/agents/              planner, generator and healer, adapted to this BDD structure
```

`.features-gen/` is generated by `bddgen`. Never edit it.

## Rules

1. **Reuse existing steps.** Never create a second step with the same text.
2. **Actions in Page Objects, assertions (`expect`) in step definitions.**
3. **Locators:** `getByTestId` (configured to saucedemo's `data-test`) first, then `getByRole`.
   No CSS/XPath unless nothing else works; explain why in a comment.
4. **No `waitForTimeout`.** Rely on auto-waiting and web-first assertions. If a pause is truly
   unavoidable, comment why (the linter warns).
5. **Scenarios are independent.** Each one prepares its own state. Preconditions use
   `Given I am logged in as a {userType} user` (a cookie, fast); the login form is used only in
   `features/auth/login.feature`.
6. **No credentials in code, scenarios or docs.** User names and the password come from the
   environment (`requireEnv` in `env.ts`, used by `src/test-data/users.ts`). Locally they are in
   `.env`, in CI in repository secrets. Scenarios may only use made-up values.
7. **Gherkin is declarative:** business actions, not clicks and selectors. Details are in the
   `gherkin-conventions` skill.
8. **Tags:** a feature tag on the `Feature:` line (`@auth`, `@cart`...); `@smoke` for the critical
   happy path only; everything else `@regression`.
9. **TypeScript:** no `any`, `import type` for types, use the path aliases from `tsconfig.json`.
10. **A new Page Object must be registered** in `src/fixtures/index.ts` (interface and `extend`).
11. **English everywhere:** code, comments, scenarios, commit messages and PR text are in English,
    even when I write to you in another language.

## Skills

## AI test agents

Playwright's test agents live in `.claude/agents/` and talk to the Playwright test MCP server from
`.mcp.json`. They are adapted to this project:

- `playwright-test-planner` explores the app and saves a plan to `specs/<area>.md`.
- `playwright-test-generator` turns a plan into BDD: a scenario, steps and Page Objects, following
  the skills. It does not write plain Playwright tests and does not use `generator_write_test`.
- `playwright-test-healer` fixes failing scenarios in steps, Page Objects or `.feature` files. It
  runs `npx bddgen` before every test run and never edits `.features-gen/`.

All of them start from `tests/seed.spec.ts` in the `agents` project (`project: "agents"`). That
project exists only when `PLAYWRIGHT_AGENTS` is set, which `.mcp.json` does for the MCP server, so
normal runs and CI never see it. The seed logs in through a cookie, so no agent types a password.

## Gotchas

- Given, When and Then are interchangeable when matching: `Given I add "X" to the cart` matches a
  step defined with `When`.
- `test_run` of the MCP server runs `playwright test` without `bddgen`. Run `npx bddgen` first,
  otherwise the tests are outdated.
- `{userType}` is a custom parameter type (`standard`, `locked out`, `problem`,
  `performance glitch`) from `features/steps/parameter-types.ts`.
- `playwright.config.ts` must list `src/fixtures/index.ts` in `steps`, otherwise `bddgen` fails with
  "Can't guess test instance".
- Allure is configured with `detail: false` on purpose: with the default, the report prints every
  typed value (`Fill "..."`), including credentials. Do not change it. Report grouping is in
  `allurerc.mjs`.
- A Pages deployment replaces the whole site, so `scripts/assemble-site.mjs` always builds `site/`
  and the reports together. Every run keeps its report in `allure/<date>/` (UTC), the five newest are
  kept and listed in `allure/runs.json`. The older reports come from the Pages artifact of the
  previous run, which is why that artifact is kept for 90 days. Never publish a report alone.
- In CI the Chromium project records a trace, a screenshot and a video for every test
  (`attachEverything` in `playwright.config.ts`), the other browsers only for failures. They stay in
  the published report on purpose. Traces and error-context files contain the typed demo
  credentials, which are public values.
- `site/index.html` reads `allure/runs.json` (`id`, `createdAt`, `total`, `passed`, `status`) to fill
  the stats and the table of the latest runs. If the format of that file changes in
  `scripts/assemble-site.mjs`, change the page in the same PR.
- Scheduled runs happen on the latest commit of `main` only. In a public repository GitHub disables
  the schedule after 60 days without repository activity; it can be enabled again in the Actions
  tab. Nightly runs are published like pushes, so they also fill the five-report archive.
- Allure history is only kept by `pages.yml` (`ALLURE_HISTORY_PATH`). Local runs build
  the report without history.
- Locally there are no retries and no traces; `CI=true` switches to the CI behaviour. Use
  `--trace on` to record a trace.

## CI

GitHub Actions has two workflows in `.github/workflows/`:

- `ci.yml` runs on every pull request, on every push to `main` and every night at 00:07 UTC
  (`schedule`, not at the full hour because GitHub delays those runs): a `quality` job
  (`npm run check`), then an `e2e` job that runs the tests in Chromium, Firefox and WebKit. The e2e
  job gets the credentials from repository secrets, and only its test step sees them.
- `pages.yml` ("Publish report") runs after `ci.yml` has finished on `main`, never for pull requests.
  It builds the Allure report from the results of that run, assembles the site and publishes it to
  GitHub Pages.

Keep both green: run `npm run check` and the tests locally before pushing.

## Git workflow

- One branch and PR per feature or concern.
- Branch names are `<type>/<name>`: the type is one of `feat`, `fix`, `chore`, `ci`, `docs`, `test`,
  `refactor`, the name is lowercase words joined by hyphens, at most 50 characters in total
  (`feat/cart`, `ci/e2e-tests`). `scripts/branch.mjs` checks it in the pre-commit hook, which also
  stops commits on `main`, and in CI for pull requests.
- Before you write or change code while on `main`, create a branch:
  `npm run branch -- create <type>/<name>`. Creating a local branch needs no asking. Committing,
  pushing and opening pull requests still do.
- Small commits in Conventional Commits style, **without a scope**: `feat: add CartPage`, never
  `feat(cart): add CartPage`. The type is one of `feat`, `fix`, `chore`, `ci`, `docs`, `test`,
  `refactor`. The description is English (plain ASCII), starts with a lowercase letter, has no
  period at the end, and the whole first line has at most 72 characters. The same goes for PR
  titles. `scripts/commit-message.mjs` checks this in the `commit-msg` hook and in CI, for the PR
  title and for every commit of a pull request.
- Do not commit, push, or open PRs unless asked. Never use `--no-verify`.
