# CLAUDE.md

UI end-to-end tests for [saucedemo.com](https://www.saucedemo.com).
Stack: **Playwright + TypeScript (strict) + playwright-bdd** (Gherkin).

I'm building this project myself, step by step, one pull request per feature. Claude helps me with
it, so work on the current task only: don't create files, folders or layers for things we haven't
reached yet.

## Commands

| Command                                                | Purpose                                                          |
| ------------------------------------------------------ | ---------------------------------------------------------------- |
| `npm test`                                             | Generate specs with `bddgen`, then run all tests in all browsers |
| `npm run test:smoke` / `npm run test:regression`       | Run only scenarios with that tag                                 |
| `npm test -- --project=chromium -g "<scenario title>"` | Run one scenario (fastest loop)                                  |
| `npx bddgen`                                           | Generate specs; prints a snippet for every missing step          |
| `npm run check`                                        | typecheck + eslint + prettier. **Run before finishing any task** |
| `npm run allure:generate` / `npm run allure:open`      | Build and open the Allure report from `allure-results/`          |
| `npm run lint:fix`                                     | Auto-fix ESLint issues                                           |
| `npm run format`                                       | Format everything with Prettier                                  |

## Structure

```
features/<domain>/*.feature  WHAT is verified, in business language (Gherkin)
features/steps/              step definitions and custom parameter types
src/pages/                   Page Objects: locators and actions, one class per page
src/fixtures/index.ts        gives steps their page objects; exports Given/When/Then/expect
src/test-data/               users and other reusable data
src/config/env.ts            typed environment config; credentials come from `.env`
allurerc.mjs                 Allure report settings (grouping, history)
site/                        source of the GitHub Pages site; the Allure report goes to `/allure/`
```

`.features-gen/` is generated by `bddgen`. Never edit it.

## Rules

1. **Reuse existing steps.** Never create a second step with the same text.
2. **Actions in Page Objects, assertions (`expect`) in step definitions.**
3. **Locators:** `getByTestId` (configured to saucedemo's `data-test`) first, then `getByRole`.
   No CSS/XPath unless nothing else works; explain why in a comment.
4. **No `waitForTimeout`.** Rely on auto-waiting and web-first assertions. If a pause is truly
   unavoidable, comment why (the linter warns).
5. **Scenarios are independent.** Each one prepares its own state.
6. **No credentials in code, scenarios or docs.** User names and the password come from the
   environment (`requireEnv` in `env.ts`, used by `src/test-data/users.ts`). Locally they are in
   `.env`, in CI in repository secrets. Scenarios may only use made-up values.
7. **Gherkin is declarative:** business actions, not clicks and selectors. Details are in the
   `gherkin-conventions` skill.
8. **Tags:** a feature tag on the `Feature:` line (`@auth`, `@cart`...); `@smoke` for the critical
   happy path only; everything else `@regression`.
9. **TypeScript:** no `any`, `import type` for types, use the path aliases from `tsconfig.json`.
10. **A new Page Object must be registered** in `src/fixtures/index.ts` (interface and `extend`).
11. **English everywhere:** code, comments, scenarios, commit messages and PR text are in English,
    even when I write to you in another language.

## Gotchas

- Given, When and Then are interchangeable when matching: `Given I add "X" to the cart` matches a
  step defined with `When`.
- `{userType}` is a custom parameter type (`standard`, `locked out`, `problem`,
  `performance glitch`) from `features/steps/parameter-types.ts`.
- `playwright.config.ts` must list `src/fixtures/index.ts` in `steps`, otherwise `bddgen` fails with
  "Can't guess test instance".
- Allure is configured with `detail: false` on purpose: with the default, the report prints every
  typed value (`Fill "..."`), including credentials. Do not change it. Report grouping is in
  `allurerc.mjs`.
- A Pages deployment replaces the whole site, so the workflow always publishes `site/` and the
  report together (report under `/allure/`). Never publish the report alone. The attachments of
  failed tests (traces, error context) stay in the published report on purpose: they contain the
  typed demo credentials, which are public values, and they show how failures are investigated.
- Allure history is only kept for runs on `main` (`ALLURE_HISTORY_PATH`, set by CI). Local runs build
  the report without history.
- Locally there are no retries and no traces; `CI=true` switches to the CI behaviour. Use
  `--trace on` to record a trace.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every pull request and on every push to
`main`: a `quality` job (`npm run check`), then an `e2e` job that runs the tests in Chromium,
Firefox and WebKit, then an `allure-report` job that merges the results of all browsers. On `main` the report is
published to GitHub Pages (`deploy-pages` job) together with `site/` and the Allure history. The e2e job gets the credentials from repository secrets, and only its test
step sees them. Keep both green: run `npm run check` and the tests locally before pushing.

## Git workflow

- One branch and PR per feature or concern (`feat/cart`, `ci/e2e-tests`, `chore/...`).
- Small commits in Conventional Commits style, **without a scope**: `feat: add CartPage`, never
  `feat(cart): add CartPage`. The same goes for PR titles.
- Do not commit, push, or open PRs unless asked. Never use `--no-verify`.
